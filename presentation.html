Attack & defense

Brute force the login. Stopped at five.

# prereq: in another terminal, from the repo root: # .venv/bin/uvicorn --factory app.main:create_app --port 8000 # sanity check — should print "server: 200" curl -s -o /dev/null -w "server: %{http_code}\n" http://localhost:8000/health # 1. loop seven wrong-password attempts against the JSON login for i in 1 2 3 4 5 6 7; do curl -s -o /dev/null -w "attempt $i → %{http_code}\n" \ -X POST http://localhost:8000/auth/login \ -H 'Content-Type: application/json' \ -d "{\"username\":\"alice\",\"master_password\":\"guess$i\"}" done
What you'll see

Stopped at five

attempts 1-5 → 401 invalid credentials
attempt 6+ → 429 too many failed attempts

Master Key 09 / 12
10 · RESIDUAL RISK Honest postmortem
Reframed

The key lives in process memory.

We proposed a weak master password as the biggest risk. After building it, the bigger architectural residual is the server-side encryption model: while a session is active, the decryption key sits in RAM.

Mitigation 01 · TTL
Sessions expire 15 minutes after creation, no sliding refresh.app/config.py · session_ttl_minutes
Mitigation 02 · Logout
Explicit logout drops the key from the in-memory store.app/auth/session_store.py · delete()
Mitigation 03 · Sweep
Background thread evicts expired keys every 60 seconds.app/auth/session_store.py · _sweep()

Master Key 11 / 12
12 · KEY DIFFERENCE vs. tutorial CRUD
The key idea

We derive the key.
We never store it.

A tutorial CRUD app stores a password in a column. We don't. PBKDF2 rebuilds the encryption key from the master password and a per-user salt at login. It lives in RAM. Process restart, key gone.

Three files. The whole idea.
app/auth/kdf.py
Derives the 32-byte key at login
app/auth/session_store.py
Holds it in memory only
app/crypto/encryption.py
Uses it for AES-256-GCM
